# 半天速成精读表

这份文档适合想在短时间内快速建立项目全局理解的同学。

目标不是逐行背代码，而是在 4 到 5 小时内回答清楚下面 5 个问题：

1. `/api/chat` 请求是怎么进系统、怎么返回的。
2. `Supervisor` 为什么存在，它怎么编排其他 Agent。
3. 这个项目里的 RAG 流程具体做了什么。
4. 三层记忆分别负责什么，怎么协作。
5. MCP 工具层和聊天链路目前的实际关系。

## 使用方法

每看完一个阶段，都做 3 件事：

- 用一句话写下这个文件在系统里的角色。
- 画出它和上下游文件的调用关系。
- 至少做一次本地验证，不要只看不跑。

## 阶段 0：5 分钟建立地图

先看：

- [README.md](../README.md)

这一阶段只抓 4 个信息：

- 这是一个多 Agent 智能客服项目。
- 入口是 FastAPI。
- 核心编排是 `Supervisor + LangGraph`。
- 能力大致分成 RAG、工单、合规、工具调用。

看完后你应该能说：

- 这个项目不是单个聊天机器人，而是多个 Agent 分工协作。

## 阶段 1：30 分钟看系统入口

先看：

- [api/main.py](../api/main.py)

重点看这些位置：

- 应用初始化：`WorkingMemory`、`ShortTermMemory`、`LongTermMemory`、`mcp_server`
- `lifespan()`：启动时做了什么（数据库 seed、知识库写入、图构建）
- `/api/chat`
- `/api/tools` / `/api/tools/call`
- 全局常量：`RECENT_TURNS`、`COMPACT_THRESHOLD`
- `_maybe_compact_history()`（滚动摘要压缩）
- `_estimate_tokens()`（Token 对比计量）

这一阶段要搞懂：

- 请求从哪里进入系统。
- `initial_state` 是怎么构造的（摘要 + 近轮原文 + 当前消息 = 按需注入）。
- `graph.ainvoke(...)` 是什么时候被调用的。
- 为什么这个接口会"等整条链路跑完"再返回。

建议验证：

- 访问 `GET /health`
- 访问 `GET /api/tools`
- 用 PowerShell 调一次 `POST /api/chat`

看完后你应该能说：

- `main.py` 是系统入口，负责启动应用、注册 API、初始化记忆和工具，并把聊天请求交给 `LangGraph` 图执行；同时负责把多轮上下文按需注入（滚动摘要 + 近轮），并用 tiktoken 计量 Token 节省。

## 阶段 2：50 分钟看编排核心

先看：

- [agents/supervisor.py](../agents/supervisor.py)

重点看这些函数：

- `decompose()`（子任务拆解 + 依赖 + 补充信息判断）
- `intent_router`（二级意图分类 + 链路规划）
- `dispatch_step()` / `collect_step()` / `check_more_steps()`（循环调度引擎）
- `synthesize_response()`（结果汇总）
- `create_supervisor_graph()`

这一阶段要搞懂：

- 为什么需要 `Supervisor`，而不是直接让一个 Agent 回答。
- 状态 `AgentState` 里都存了什么（尤其 `sub_tasks` / `dependencies` / `task_chains` / `task_results`）。
- `dispatch_mode`（chain / parallel / dependent）是怎么回事 —— 当前以**串行循环 + 依赖条件**为主，并行是预留。
- 路由是怎么决定走 `knowledge_rag`、`ticket_handler` 的。
- 为什么最后还要再经过一次 `synthesize_response()`。

建议你边看边画图：

- `supervisor_decompose -> intent_router -> dispatch_step（循环）-> collect_step -> check_more_steps -> compliance_check -> synthesize`

> 注意：图节点实际命名为 `supervisor_decompose` / `intent_router` / `dispatch_step` / `collect_step` / `compliance_check` / `synthesize` 等，README 里的旧图是简化示意。

建议验证：

- `create_supervisor_graph(enable_checkpointing=True)` 能编译出包含上述节点的图。

看完后你应该能说：

- `supervisor.py` 是全项目核心，负责子任务拆解、依赖管理、循环执行引擎和最终结果汇总。

## 阶段 3：45 分钟看 RAG 主流程

先看：

- [agents/knowledge_rag.py](../agents/knowledge_rag.py)
- [memory/long_term.py](../memory/long_term.py)（只关注检索部分）

重点看这些函数：

- `rewrite_query()`（Query 改写）
- `retrieve_documents()` —— 内部走 `long_term_memory.hybrid_search()`
- `hybrid_search()`（`long_term.py`）：FAISS 向量 + BM25 双路召回 → RRF 融合
- `rerank_documents()` —— Cross-Encoder 精排，离线不可用降级 LLM 重排
- `generate_answer()`
- `process()`

这一阶段要搞懂：

- 这个项目的 RAG 不是一句话，而是 **Query 改写 → 双路召回 → RRF 融合 → Rerank 精排 → 生成**。
- 为什么向量和 BM25 要双路召回（语义 vs 专有名词互补）。
- `process()` 最后写回到了哪里（`sub_results` / `task_results`）。

建议你记住这条链：

- Query Rewrite
- Hybrid Recall (FAISS + BM25)
- RRF Fusion
- Rerank
- Generate

建议验证：

- 运行 `python eval/rag_eval.py`，观察"向量单路 / BM25 单路 / 混合(RRF)"三路指标对比。

看完后你应该能说：

- `knowledge_rag.py` 实现了一套混合召回 RAG 链路，检索底座是 `long_term.py` 的 FAISS + BM25 + RRF。

## 阶段 4：35 分钟看长期记忆和混合检索

先看：

- [memory/long_term.py](../memory/long_term.py)

重点看这些函数：

- `_init_embedder()` / `_init_index()`
- `get_embedding()`（sentence-transformers，不可用降级哈希）
- `add_document()` / `add_documents_batch()`
- `search()`（向量单路）
- `_rebuild_bm25()` / `_tokenize_text()`（jieba 分词）
- `hybrid_search()`（双路召回 + RRF）
- `load_knowledge_base()`

这一阶段要搞懂：

- 为什么它叫"长期记忆"。
- 它和 RAG 的关系是什么。
- FAISS 在这里起什么作用。
- `hybrid_search()` 的 RRF 融合逻辑。

这一步尤其要注意：

- `sentence-transformers` 不可用时，embedding 会降级为哈希向量（语义检索退化为近似），**部署时务必装上依赖**（见 `requirements.txt`）。

建议验证：

- `python -c "from memory.long_term import LongTermMemory; m=LongTermMemory(index_path='./vector_store/_t'); m.add_document('金葵理财收益3.5%-5.2%','p.md'); print(m.hybrid_search('金葵理财收益',top_k=3))"`

看完后你应该能说：

- `LongTermMemory` 是 RAG 的检索底座，提供"向量单路 + BM25 + RRF 混合召回"，是混合检索的关键。

## 阶段 5：25 分钟看短期记忆

先看：

- [memory/short_term.py](../memory/short_term.py)
- [api/main.py](../api/main.py) 的 `_maybe_compact_history()`

重点看这些函数：

- `_get_redis()`
- `add_message()` / `get_history()`
- `set_summary()` / `get_summary()`（滚动摘要的存取）
- `get_injection_context()`（摘要 + 近轮原文）
- `get_context_window()`（按 token 窗口截断）

这一阶段要搞懂：

- Redis 可用时和不可用时分别怎么工作（内存降级）。
- 多轮对话上下文是怎么保存的（TTL 30 分钟 + 20 轮滑动窗口）。
- **滚动摘要压缩**：新增未压缩消息超过 `COMPACT_THRESHOLD` 时，把旧消息用 LLM 压缩进摘要，只保留最近 `RECENT_TURNS` 轮原文。
- 为什么按需注入能降低 Token 消耗。

建议验证：

- 运行 `python eval/token_compression_eval.py` 看"全量 vs 按需注入"的 Token 对比。

看完后你应该能说：

- `ShortTermMemory` 负责会话级上下文保存，优先 Redis、内存降级；配合 `api/main.py` 的滚动摘要实现按需注入，控制 Prompt Token。

## 阶段 6：35 分钟看工具层

建议验证：

## 阶段 7：30 分钟看合规和业务 Agent

先看：

- [agents/compliance_checker.py](../agents/compliance_checker.py)
- [agents/ticket_handler.py](../agents/ticket_handler.py)

这一阶段不用逐行死抠，重点看职责划分：

- `compliance_checker.py`：规则引擎（PII + 违规金融用语正则）+ LLM 深度审查 + PII 脱敏，调 MCP `risk_check`
- `ticket_handler.py`：LLM 判断 action（create/query/update/need_info），经 MCP 落 SQLite；退款/理赔会把订单状态改 `refunding`；缺信息用 ⚠️ 配合工作记忆多轮补充

这一阶段要搞懂：

- 为什么客服系统里不只有 RAG。
- 为什么最终回答前还要合规检查。
- 为什么工单类请求更像业务动作而不是知识问答。

看完后你应该能说：

- 这个项目不是只有"问答"，还包含业务执行（工单/订单）和内容治理（合规/脱敏）两个方向。

## 阶段 8：20 分钟看评测

先看：

- [eval/rag_eval.py](../eval/rag_eval.py)
- [eval/ragas_judge.py](../eval/ragas_judge.py)
- [eval/token_compression_eval.py](../eval/token_compression_eval.py)

重点理解：

- 离线 IR 指标：Context Precision / Recall / MRR / Hit@K，支持三路召回横向对比
- RAGAS 风格 LLM-as-Judge：Context Precision / Context Recall（与简历口径一致）
- Token 压缩评测：全量 vs 按需注入的 Token 节省

建议验证：

```bash
python eval/rag_eval.py                    # 离线 IR 指标
python eval/ragas_judge.py --samples 24    # RAGAS 口径（需 LLM 配置）
python eval/token_compression_eval.py      # Token 节省
```

看完后你应该能说：

- 项目有可复现的 RAG 检索评测和 Token 优化量化，能支撑简历上的指标数字。

## 半天后你该进入什么阶段

如果你已经完成这份精读表，下一步最值得做的是二选一：

- 做一次工程增强：把 `/api/chat` 的按需注入 Index 参数（`RECENT_TURNS` / `COMPACT_THRESHOLD`）调优，观察 Token 与回答质量的 trade-off。
