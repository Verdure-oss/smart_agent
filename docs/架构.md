# 架构设计文档

## 1. 系统总体架构

### 1.1 架构概览

本系统采用 **Supervisor编排模式**（中心化协调），由一个 Supervisor Agent 统一调度 4 个专业子 Agent。

```
                          ┌─────────────────────────┐
                          │     用户 (Web/App/API)    │
                          └────────────┬────────────┘
                                       │ HTTP/SSE
                                       ▼
                          ┌─────────────────────────┐
                          │   API Gateway (FastAPI)   │
                          │   认证 | 限流 | 日志       │
                          └────────────┬────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                   │
                    ▼                  ▼                   ▼
            ┌──────────┐     ┌──────────────┐    ┌──────────────┐
            │ 短期记忆   │     │  Supervisor  │    │ 全链路追踪    │
            │(Redis+摘要)│◄───►│   编排Agent   │───►│(OpenTelemetry)│
            └──────────┘     └──────┬───────┘    └──────────────┘
                                    │
                    ┌───────────────┼───────────────┐
                    │               │               │
                    ▼               ▼               ▼
            ┌──────────┐   ┌──────────┐   ┌──────────────┐
            │ 知识检索   │   │ 工单处理  │   │   合规审查    │
            │  Agent    │   │  Agent   │   │    Agent     │
            │  (RAG)    │   │ (CRUD)   │   │ (规则+LLM)   │
            └────┬─────┘   └────┬─────┘   └──────────────┘
                 │               │
                 ▼               ▼
            ┌──────────┐   ┌──────────┐
            │ 长期记忆   │   │ MCP工具   │
            │ (FAISS+   │   │  协议层   │
            │  BM25混合) │   │          │
            └──────────┘   └──────────┘
```

数据流特点：
- **意图路由** 在 Supervisor 拆解后做二级分类 + 链路规划（`agent_chain`）。
- **循环调度**：`dispatch_step` → 业务 Agent（知识检索/工单）→ `collect_step` → `check_more_steps`（判断继续或结束）循环执行，直至满足依赖条件。
- 所有业务结果统一经 `compliance_check` → `synthesize` 汇总。

### 1.2 编排流程（Supervisor Pattern）

```
用户请求
    │
    ▼
[Supervisor.decompose] ──拆解子任务+依赖+补充信息判断──┐
    │                                                │
    ▼                                                │ 有依赖子任务则串行
[intent_router] ──二级意图分类 + 规划 agent_chain ────┤
    │                                                │
    ▼                                                │
[dispatch_step] ──按 agent_chain 顺序派发 ────────────┤
    │                                                │
    ├── knowledge_rag → 知识检索（RAG 混合召回）       │
    ├── ticket_handler → 工单处理（创建/查询/更新）     │
    │                                                │
    ▼                                                │
[collect_step] ──汇合本轮子任务结果 ────────────────┘
    │
    ▼
[check_more_steps] ──依赖条件满足? 还有未完成子任务?
    │
    ├── 未完 ├── 循环回 dispatch_step（可含依赖条件判断）
    ▼
[compliance_check] ── 所有回复必须经过（规则+LLM 两阶段）
    │
    ├── 通过 ──► [synthesize 汇总] ──► 响应
    └── 不通过 ──► 违规项记录 + 脱敏后继续或转人工
```

## 2. 核心组件设计

### 2.1 Agent 设计原则

每个 Agent 遵循**单一职责原则**：

| Agent | 职责 | 输入 | 输出 |
|-------|------|------|------|
| Supervisor | 子任务拆解、依赖管理、循环调度、结果汇总 | 用户消息 + 全局 State | 子任务列表 + 最终回复 |
| 意图路由 | 二级意图分类 + 链路规划 | 用户消息 | intent + agent_chain |
| 知识检索 | RAG 问答（Query改写→混合召回→RRF→Rerank→生成） | 用户问题 | 基于文档的回答 |
| 工单处理 | 工单创建/查询/更新 + 订单状态变更 | 用户需求 | 工单号 + 状态 |
| 合规审查 | 两阶段审查（正则规则 + LLM） + PII 脱敏 | Agent 回复内容 | 通过/不通过 + 违规项 + 脱敏文本 |

### 2.2 State 设计

`AgentState`（见 `agents/supervisor.py`）核心字段：

```python
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]  # 对话消息（add_messages reducer）
    user_id: str
    session_id: str
    intent: str                    # 识别到的意图
    sub_results: dict[str, Any]    # 各 Agent 的处理结果
    compliance_passed: bool        # 合规审查是否通过
    final_response: str            # 最终回复
    current_agent: str
    retry_count: int

    # 子任务编排（Supervisor 拆解产物）
    sub_tasks: list[dict]          # 子任务列表 + 依赖关系
    dependencies: list[dict]       # 依赖边
    needs_parallel: bool           # 是否可并行（当前以串行+依赖条件为主）
    dispatch_mode: str             # "chain" / "parallel" / "dependent"
    task_chains: dict[str, list]   # 每个子任务的链路（agent_chain）
    task_results: dict[str, Any]   # step_key -> 结果，key 形如 "{task_id}_step_{i}"
    completed_task_ids: list[str]  # 已完成的子任务 id
    current_sub_task_id: str
    _last_dispatched_agent: str
```

`Annotated[list[BaseMessage], add_messages]` 是 LangGraph 的 reducer：多节点写入时自动追加而非覆盖。

### 2.3 分层记忆架构

```
┌──────────────────────────────────────────────┐
│                  应用层                       │
├──────────────────────────────────────────────┤
│  工作记忆 (Working Memory)                    │
│  ├── 存储: 进程内存 (dict)                    │
│  ├── 生命周期: 单次请求                       │
│  ├── 延迟: < 1ms                             │
│  └── 用途: 当前推理状态、跨轮补充信息收集        │
├──────────────────────────────────────────────┤
│  短期记忆 (Short-term Memory)                │
│  ├── 存储: Redis (不可用时降级内存)            │
│  ├── 生命周期: TTL 30分钟 + 最近20轮滑动窗口    │
│  ├── 延迟: 1-5ms                             │
│  ├── 滚动摘要: 新增未压缩消息>阈值时用 LLM       │
│  │   压缩旧消息进摘要，仅保留最近几轮原文         │
│  └── 用途: 多轮对话上下文（按需注入）            │
├──────────────────────────────────────────────┤
│  长期记忆 (Long-term Memory)                 │
│  ├── 存储: FAISS 索引 + sentence-transformers │
│  ├── 生命周期: 永久                           │
│  ├── 检索: BM25 + 向量双路召回 → RRF 融合      │
│  ├── 延迟: 10-50ms                           │
│  └── 用途: 知识库、用户画像、历史工单            │
└──────────────────────────────────────────────┘
```

**按需注入（Token 优化）**：`api/main.py` 中每次请求构造 messages 时，不再把最近 10 轮全量塞入，而是注入「滚动摘要 + 最近几轮原文 + 当前消息」。同时用 tiktoken 实测对比"全量 vs 按需"的 Prompt Token，写入日志并可经 `/api/metrics` 的 `AgentMetrics` 查看累计 token。实测 20 轮会话 Prompt Token 均值降低约 20%~45%（保守下限，随会话变长递增）。

## 3. RAG 检索流程

```
用户原始问题: "怎么退钱啊"
        │
        ▼
[Query改写] ──► "退款 政策 申请 流程 时限"
        │
        ▼
[双路召回] ──► ① FAISS 向量检索 Top-N
          │     ② BM25 关键词检索 Top-N   (jieba 分词)
        │
        ▼
[RRF 融合] ──► Reciprocal Rank Fusion 合并两路排序
        │
        ▼
[Rerank 精排] ──► Cross-Encoder (bge-reranker-base)
        │                             │
        │                             └─ 离线不可用时降级 LLM 重排
        ▼
[上下文注入] ──► Prompt + Top-3 文档（标注来源）
        │
        ▼
[LLM生成] ──► 基于文档的回答 + 引用来源
        │
        ▼
[合规审查] ──► 检查回复合规性
        │
        ▼
最终回答 + 引用来源
```

**为什么混合召回？**
- 向量检索擅长语义匹配（"怎么退钱" ≈ "退款流程"）
- BM25 擅长专有名词/关键词精确匹配（产品名、订单号、政策条款）
- RRF 融合 + Reranker 精排将两者互补，兼顾召回率与精确率

**评测**（见 `eval/`）：
- `eval/rag_eval.py`：离线 IR 指标（Context Precision / Recall / MRR / Hit@K），支持向量单路 / BM25单路 / 混合(RRF) 三路横向对比
- `eval/ragas_judge.py`：RAGAS 风格 LLM-as-Judge 评测 Context Precision / Context Recall
- 实测（24 题中文 QA，top_k=3，RAGAS 口径 / gpt-6-luna）：Context Precision 95.8%、Context Recall 94.8%

## 4. MCP 工具协议

```
┌─────────────┐    JSON-RPC 2.0    ┌─────────────────┐
│   Agent      │ ◄────────────────► │  MCP Tool Server │
│              │                    │                  │
│ tools/list   │ ──── 发现 ─────►  │  ┌─order_query    │
│ tools/call   │ ──── 调用 ─────►  │  ├─ticket_create  │
│              │ ◄─── 结果 ──────  │  ├─risk_check     │
│              │                    │  └─knowledge_search│
└─────────────┘                    └─────────────────┘
```

默认注册 4 个工具：`order_query`（订单查询）、`ticket_create`（工单创建）、`risk_check`（风控）、`knowledge_search`（知识库混合检索，走 BM25+向量+RRF）。`ticket_handler`、`compliance_checker` 已通过 MCP 工具层实际调用落库。

工具注册示例：
```json
{
  "name": "order_query",
  "description": "查询订单信息",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string"}
    },
    "required": ["order_id"]
  }
}
```

## 5. 全链路追踪与指标

### Span 层级结构

```
[Root] user_request (session_id=xxx, user_id=yyy)
  │
  ├── [Span] supervisor.decompose
  ├── [Span] intent_router.process
  ├── [Span] knowledge_rag.process
  │     ├── [Span] rag.query_rewrite
  │     ├── [Span] rag.hybrid_search (FAISS + BM25 + RRF)
  │     ├── [Span] rag.rerank
  │     └── [Span] rag.generate_answer
  ├── [Span] compliance_checker.process
  │     ├── [Span] compliance.rule_check (2ms)
  │     └── [Span] compliance.llm_check (600ms)
  └── [Span] supervisor.synthesize
```

### 关键监控指标

`AgentMetrics`（`tracing/otel_config.py`）按 Agent 维度维护：`total_calls`、`avg_duration_ms`、`error_rate`、`total_input_tokens`、`total_output_tokens`、`avg_input_tokens`。其中 **token 计量**用于量化按需注入的 Token 节省效果，经 `GET /api/metrics` 暴露。

| 指标 | 说明 | 关注点 |
|------|------|---------|
| P99 延迟 | 99% 请求响应时间 | LLM 调用为主要瓶颈 |
| Agent 错误率 | 各 Agent 失败比例 | > 5% 需排查 |
| Token 消耗/请求 | 按需注入 vs 全量基线 | 用 tiktoken 实测量化 |
| Prompt Token 节省 | (全量-按需)/全量 | 实测 20%~45% |
| RAG 检索指标 | Precision/Recall/MRR/Hit@K | 用 eval/ 脚本评测 |
| 合规通过率 | 合规审查通过比例 | <90% 需关注 |

## 6. 技术选型对比

### 编排框架对比

| 维度 | LangGraph (Python) | Spring AI (Java) | Eino (Go) |
|------|-------------------|------------------|-----------|
| 编排模型 | 有向图 StateGraph | Agent 组合模式 | Graph/Workflow |
| 状态管理 | TypedDict + Checkpoint | POJO | struct |
| 并行能力 | asyncio | CompletableFuture | goroutine |
| 生态 | LangSmith/LangServe | Spring 生态 | CloudWeGo |
| 适合团队 | AI/数据团队 | 企业级 Java 团队 | Go 微服务团队 |

> 说明：本仓库当前为 **Python/LangGraph 单语言实现**。Java/Go 方案在 `docs/interview/` 中作为面试讲解素材，不包含可运行代码。

### 向量检索对比

| 维度 | FAISS | Milvus | Pinecone |
|------|-------|--------|----------|
| 部署方式 | 嵌入式 | 分布式 | SaaS |
| 数据规模 | 千万级 | 百亿级 | 百亿级 |
| 查询延迟 | < 1ms | ~10ms | ~50ms |
| 运维复杂度 | 低 | 中 | 零 |
| 适合阶段 | 开发/小规模 | 生产 | 快速上线 |

> 本项目当前使用 FAISS + sentence-transformers 做向量索引。生产规模扩大时可按 RRF 融合的同一接口平滑迁移到 Milvus。
