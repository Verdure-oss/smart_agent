## 1. Supervisor 编排 (supervisor.py)

### 1.1 State 定义 — 系统的"数据总线"

```python
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    user_id: str
    session_id: str
    intent: str
    sub_results: dict[str, Any]
    compliance_passed: bool
    final_response: str
    current_agent: str
    retry_count: int

    # 子任务编排字段
    sub_tasks: list[dict]           # 子任务 + 依赖
    dependencies: list[dict]        # 依赖边
    needs_parallel: bool
    dispatch_mode: str              # chain / parallel / dependent
    task_chains: dict[str, list]    # {task_id: [agent, agent, ...]}
    task_results: dict[str, Any]    # {step_key: result}
    completed_task_ids: list[str]
    current_sub_task_id: str
    _last_dispatched_agent: str
```

**设计要点**：
- `Annotated[list[BaseMessage], add_messages]`：LangGraph 的 reducer 机制，多节点写入 messages 时自动追加而非覆盖。
- `sub_results` / `task_results` 是 dict：各 Agent 把结果写入不同 key，避免互相覆盖。
- `compliance_passed` 是布尔值：合规审查的结果，决定最终是否放行自动回复。

### 1.2 图构建与节点

```python
builder = StateGraph(AgentState)
builder.add_node("supervisor_decompose", supervisor.decompose)
builder.add_node("intent_router", intent_agent.process)
builder.add_node("dispatch_step", supervisor.dispatch_step)
builder.add_node("knowledge_rag", knowledge_agent.process)
builder.add_node("ticket_handler", ticket_agent.process)
builder.add_node("collect_step", supervisor.collect_step)
builder.add_node("compliance_check", compliance_agent.process)
builder.add_node("synthesize", supervisor.synthesize_response)
```

- **入口**：`supervisor_decompose`
- **条件边**：`collect_step` 后根据 `check_more_steps` 决定循环 `dispatch_step` 继续，还是走向 `compliance_check`
- **固定边**：`compliance_check -> synthesize -> END`
- **Checkpoint**：`MemorySaver()` 保存每步 State 快照

**设计模式**：
- **条件循环**：`dispatch_step` ⇄ `collect_step` 构成子任务执行循环，配合 `dependencies` 判断依赖条件是否满足（LLM 评估，如"收益率>5%才购买"）。
- **汇聚点**：`compliance_check` 确保所有回复都经过审查。
- **Checkpoint**：支持断点恢复（Human-in-the-Loop 的基础）。

> 说明：`dispatch_mode="parallel"` / `needs_parallel` 数据结构已就绪，但当前实际执行以**串行循环 + 依赖条件**为主（一次派发一个子任务的下一跳）。面试时不要声称已实现真并行。

## 2. RAG 知识检索 (knowledge_rag.py + long_term.py)

### 2.1 完整 RAG 流程（混合召回）

```python
async def process(self, state):
    original_query = messages[-1].content

    # Step 1: Query 改写（口语 → 检索友好）
    rewritten_query = await self.rewrite_query(original_query)

    # Step 2: 双路召回 + RRF 融合（FAISS 向量 + BM25）
    raw_docs = await self.retrieve_documents(rewritten_query, top_k=top_k)
    #   内部 → long_term_memory.hybrid_search(query, top_k)

    # Step 3: Rerank 精排（Cross-Encoder，离线降级 LLM 重排）
    reranked_docs = await self.rerank_documents(rewritten_query, raw_docs, top_k=3)

    # Step 4: 生成回答（Prompt 约束回答边界 + 标注引用来源）
    answer = await self.generate_answer(original_query, reranked_docs)
```

### 2.2 混合召回 (long_term.py)

```python
def hybrid_search(self, query, top_k=5, fusion_k=60):
    # 1) 向量召回（FAISS 余弦/IP）
    vector_docs = self.search(query, top_k=top_k)

    # 2) BM25 召回（jieba 分词，rank_bm25；不可用降级 _SimpleBM25）
    if self._bm25 is None or self._bm25_dirty:
        self._rebuild_bm25()
    bm25_scores = self._bm25.get_scores(_tokenize_text(query))
    ...

    # 3) RRF 融合：score += 1 / (fusion_k + rank)
    for rank, d in enumerate(vector_docs):
        rrf[key] += 1.0 / (fusion_k + rank + 1)
    for rank, d in enumerate(bm25_docs):
        rrf[key] += 1.0 / (fusion_k + rank + 1)
    # 按 RRF 分降序取 top_k
```

**RRF 原理**：不比较两路的绝对分数（量纲不同），只按排序位置融合 `1/(k + rank)`，对两路都靠前的文档给高分。`k=60` 是经验值，缓解排名靠后文档的分数衰减。

**为什么混合召回**：向量擅长语义近义（"怎么退钱"≈"退款流程"），BM25 擅长专有名词精确匹配（产品名、订单号）。单路向量对专有名词易失真，混合召回是其短板互补。

**为什么先召回再 Rerank 到 Top-3**：
- 双路召回保证召回率（Top-K 更宽）
- Reranker（Cross-Encoder）做更精确的相关性排序，从候选筛到 3 篇
- 最终只注入 3 篇文档，控制 Token

**评测**（`eval/`）：
- `rag_eval.py`：离线 IR 指标，三路横向对比（向量单路 / BM25 单路 / 混合 RRF）
- `ragas_judge.py`：RAGAS 风格 LLM-as-Judge，实测（24 问，top_k=3）Context Precision ≈95.8%、Context Recall ≈94.8%

`api/main.py` 中的增量压缩逻辑（核心）：

```python
async def _maybe_compact_history(session_id):
    full = await short_term_memory.get_history(session_id)
    summary_text, compacted_upto = await short_term_memory.get_summary(session_id)

    if len(full) - compacted_upto <= COMPACT_THRESHOLD:   # 未压缩的新消息未超阈值 → 跳过
        return

    cutoff = max(compacted_upto, len(full) - RECENT_TURNS)
    old_msgs = full[compacted_upto:cutoff]                 # 旧消息压缩，保留最近几轮
    new_summary = await llm.invoke(SUMMARY_COMPACT_PROMPT) # LLM 生成/合并摘要（保留实体/待办，丢弃寒暄）
    await short_term_memory.set_summary(session_id, new_summary, cutoff)
```

**关键点**：
- 只在新增未压缩消息数 > `COMPACT_THRESHOLD(6)` 时才触发一次 LLM 压缩，避免每次都调用。
- `compacted_upto` 记录已压缩到的消息条数，支持增量压缩。
- 压缩失败自动跳过，不影响主流程（try/except）。

## 4. 合规审查 (compliance_checker.py)

### 4.1 两阶段审查机制

```python
async def full_check(self, content: str) -> ComplianceResult:
    # Phase 1: 规则引擎（毫秒级，零成本）—— PII + 违规金融用语正则
    rule_result = await self.rule_check(content)

    # 高风险直接拦截，不走 LLM
    if not rule_result.passed and rule_result.risk_level in ("high", "critical"):
        return rule_result

    # Phase 2: LLM 深度审查（秒级，有 API 成本） + PII 脱敏
    llm_result = await self.llm_check(content)
    ...
```

**设计要点**：
- 规则引擎是高召回的**快筛**（宁可多报不漏报）；LLM 审查是高精度的**精筛**。
- 高风险直接拦截不走 LLM：省成本又降延迟。
- 输出含脱敏文本（清洗 PII），合规通过后传给汇总，供最终回复使用。

def trace_agent_call(agent_name: str):

## 7. 设计模式总结

| 模式 | 应用位置 | 说明 |
|------|---------|------|
| **策略模式** | 意图路由 Agent | 不同意图使用不同处理链路 |
| **责任链模式** | 合规审查 | 规则引擎 → LLM 审查，逐层过滤 |
| **装饰器模式** | OpenTelemetry 追踪 | 无侵入添加追踪能力 |
| **工厂模式** | MCP 工具注册 | 统一工具创建和注册接口 |
| **状态模式** | 工单状态流转 | created → processing → resolved / refunding |
| **观察者模式** | 全链路追踪 | Agent 执行事件自动触发 Span 记录 |
| **单例模式** | 记忆系统 | 工作记忆、短期记忆全局唯一实例 |

面试时提到设计模式可以加分，但要结合具体场景说明为什么用这个模式，而不是为了用而用。
